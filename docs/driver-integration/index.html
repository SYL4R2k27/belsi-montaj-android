BELSI.Команда — единая система для стройки

Единый дизайн и стек с BELSI.Монтаж. Driver и Logistician добавляются как новые роли через capabilities-модель: один аккаунт может работать в нескольких режимах с переключением в шапке. Документ описывает все экраны, дизайн-токены и архитектурные решения.

Контекст

Зафиксированные решения

Эти ответы получены в обсуждении и стали основой архитектуры. Решения отмеченные ⏳ ещё уточняются.

✅ Capabilities-модель
У пользователя есть базовая role и массив capabilities[]. До 2 capabilities на одного юзера. Сервер контролирует доступ к endpoint-ам по capability.
✅ Заявка → Маршрут
Двухуровневая модель. Координатор/Бригадир создают заявки. Логист объединяет заявки в маршруты, назначает водителя. Куратор может всё.
✅ Переключатель в шапке (1.D)
Через меню «⋮» с явным статусом текущей роли + бейджик-точка когда в фоне есть процесс другой роли + tutorial при первом запуске.
✅ Диалог при смене роли
Переключение запрашивает подтверждение. Стратегия 3: умные дефолты (пауза/завершить/оставить) на основе контекста смены.
✅ Curator-Logistician — дуальный паттерн
Точно как Driver-Installer. Куратор может иметь capability логиста и переключаться. Главный + диспетчер в маленькой компании.
✅ История объекта
Единая лента всех событий объекта: создание, фото, смены, доставки, инструменты, задачи. Доступна всем ролям с фильтрами по роли.
✅ Logistician — отдельная роль
Основная функция: контроль маршрута. Не управляет ролями (это куратор), не модерирует фото монтажа.
✅ Правка маршрута после старта
Логист и куратор могут добавлять PENDING-точки в активный маршрут. Доставленные (DELIVERED) — нельзя править. Текущие (ARRIVED) — только куратор может отменить.

Architecture

Поток заявка → маршрут

Двухуровневая модель. Координатор/Бригадир описывают потребность, не думая о водителях. Логист объединяет заявки в эффективные маршруты и назначает водителя.

📋 Координатор / Бригадир
Создаёт заявку:
«Нужно X на объект Y к времени Z»
→
🚛 Логист
Видит все pending-заявки. Объединяет в маршрут, назначает водителя.
💼 Водитель
Получает push, открывает маршрут, едет по точкам PICKUP / DELIVERY / RETURN.
→
🛠 Бригадир на объекте
Push «груз прибыл», подтверждает приёмку. Заявка получает финальный fulfilled.

Связь данных

delivery_request                    routes                    delivery_points
├── id                              ├── id                    ├── id
├── site_object_id ────FK──┐         ├── driver_id             ├── route_id ──FK──→
├── created_by             │         ├── status               ├── sequence
├── what (text)            │         └── scheduled_for         ├── point_type:
├── needed_by (datetime)   │                                  │     PICKUP|DELIVERY
├── status:                │                                  │     |TRANSIT|RETURN
│     pending → assigned   │                                  ├── address
│     → fulfilled          │                                  ├── site_object_id ──FK
└── route_id ──FK──────────┘                                  ├── status: PENDING|ARRIVED|DELIVERED
                                                              └── linked_request_id ──FK
UX · Critical flow

Смена ролей

Концепт: смена и маршрут — разные сущности. Переключение влияет только на смену (таймер). Маршрут — это чек-лист точек, между точками время не учитывается.

Стратегия: умный диалог

При переключении из Installer → Driver система спрашивает что сделать с активной сменой: пауза, завершить или оставить активной. Радио-кнопка предзаполняется по эвристике (длительность смены, локация).

Эвристика дефолтов

КонтекстДефолт
Смена меньше 30 минЗавершить (короткая операция)
Маршрут не на этом объектеПауза (уезжает не скоро)
Маршрут идёт на этот же объектОставить активной (вернётся)
По умолчаниюПауза
